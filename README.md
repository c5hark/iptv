# IPTV backend

Небольшой бэкенд IPTV/OTT-сервиса на Go: REST API отдаёт абоненту список доступных ему ТВ-каналов и ссылку на live-поток (HLS). Доступ только для аутентифицированных пользователей (HTTP Basic Auth). Доступ к каналам определяется подписками.

## Запуск

### Через Docker

```
docker compose up --build
```

Сервис будет доступен на `http://localhost:8080`. База хранится в docker volume `iptv-data` и переживает перезапуск. Чтобы начать с чистой базой: `docker compose down -v`.

### Локально

Нужен Go 1.27+.

```
go run ./cmd/iptv
```

Файл базы `iptv.db` появится в текущей папке. При первом запуске создаётся схема и тестовые данные.

### Конфигурация

Настройки задаются переменными окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `IPTV_ADDR` | `:8080` | адрес HTTP-сервера |
| `IPTV_DB_PATH` | `iptv.db` | путь к файлу SQLite |
| `IPTV_STREAM_BASE_URL` | `http://stream.example.com` | база для ссылок на потоки |

### Тесты

```
go vet ./...
go test ./...
```

Внешнее окружение не нужно: тесты поднимают SQLite во временной папке.

## Примеры запросов

В PowerShell вместо `curl` пишите `curl.exe`.

```
# Список доступных каналов
curl -i -u alice:alice-pass http://localhost:8080/api/v1/channels

# Ссылка на просмотр канала
curl -i -u alice:alice-pass http://localhost:8080/api/v1/channels/1/playback

# Без авторизации: 401 + WWW-Authenticate
curl -i http://localhost:8080/api/v1/channels

# Канал без действующей подписки: 403
curl -i -u bob:bob-pass http://localhost:8080/api/v1/channels/4/playback

# Выключенный канал: 404
curl -i -u alice:alice-pass http://localhost:8080/api/v1/channels/6/playback

# Некорректный id: 400
curl -i -u alice:alice-pass http://localhost:8080/api/v1/channels/abc/playback
```

Пример ответа со списком:

```json
{"channels":[{"id":1,"number":1,"name":"Первый"},{"id":2,"number":2,"name":"Россия 1"}]}
```

Пример ответа со ссылкой:

```json
{"channel_id":1,"url":"http://stream.example.com/live/ch1/index.m3u8"}
```

Ошибки всегда имеют один формат и не содержат внутренних подробностей:

```json
{"error":{"code":"forbidden","message":"no active subscription for this channel"}}
```

| Ситуация | Код | `error.code` |
|---|---|---|
| нет или неверные учётные данные, пользователь выключен | 401 | `unauthorized` |
| `id` не положительное целое число | 400 | `invalid_id` |
| канал существует, но нет действующей подписки | 403 | `forbidden` |
| канала нет или он выключен | 404 | `not_found` |
| внутренняя ошибка (детали только в логе) | 500 | `internal` |

Дополнительно есть `GET /healthz` без авторизации (для healthcheck).

## Реализованные усложнения

### Подписки (реализовано)

- Подписка выдаётся на **пакет каналов** (таблицы `packages`, `package_channels`, `subscriptions`).
- Два вида подписок: **бессрочная** (`expires_at IS NULL`; администратор включает и выключает её через `is_active`) и **ограниченная по времени** (`expires_at` в будущем). После `expires_at` доступ пропадает сам, без фоновых задач: условие «подписка действует» вычисляется в SQL на момент запроса. Ровно в момент `expires_at` подписка уже не действует.
- `GET /api/v1/channels` возвращает **только доступные** каналы.
- `GET /api/v1/channels/{id}/playback`: 404, если канала нет или он выключен (даже если он входит в оплаченный пакет); **403**, если канал существует, но подписки на него нет.

## Структура

```
cmd/iptv/          точка входа: конфиг, запуск, корректная остановка
internal/config/   чтение переменных окружения
internal/store/    SQLite: схема, тестовые данные, запросы (пользователи, каналы, подписки)
internal/auth/     middleware Basic Auth
internal/api/      маршруты и обработчики
internal/httpx/    JSON-ответы и единый формат ошибок
```

## Ключевые решения и компромиссы

**Стандартная библиотека.** Роутинг через `http.ServeMux` (методы и `{id}` в шаблонах поддерживаются с Go 1.22), логи через `log/slog` в JSON, тесты через `httptest`. Фреймворки и ORM не нужны для такого объёма.

**Зависимости.**
- `modernc.org/sqlite` — драйвер SQLite на чистом Go. Не требует CGO, поэтому Docker-сборка простая, а бинарник статический.
- `golang.org/x/crypto` (пакет `bcrypt`) — хэширование паролей. В stdlib нет подходящего медленного хэша для паролей.

**Пароли** хранятся только как bcrypt-хэш. Для несуществующего логина всё равно выполняется сравнение с фиктивным хэшем, чтобы по времени ответа нельзя было определить, существует ли логин.

**Одинаковый 401** для всех причин отказа (нет пользователя, неверный пароль, пользователь выключен): клиент не узнаёт, какая именно проверка не прошла. Длина логина и пароля ограничена 256 байтами, чтобы не гонять bcrypt на огромном вводе.

**Выключенный канал даёт 404**, как и несуществующий: клиенту незачем знать о каналах, которые он видеть не должен.

**403 для канала без подписки** раскрывает, что канал с таким id существует. Это сознательный выбор ради понятной ошибки для клиента; 404 скрывал бы существование, но клиенту было бы сложнее понять причину отказа. Список каналов при этом показывает только доступные.

**Список только с доступными каналами**, а не «все с признаком доступности»: абонент не видит то, что ему недоступно, ответ короче. Минус в том, что нельзя показать абоненту, что ещё можно подключить.

**Подписки.**
- Одна запись на пару «пользователь и пакет»: продление это обновление `expires_at`. Минус: история подписок не хранится.
- `expires_at` хранится числом (секунды Unix, UTC): сравнение числом проще и не зависит от формата строк и часовых поясов.
- Текущее время передаётся в запрос параметром, а не берётся из SQL: логику можно проверять тестами на любой момент («через два года») без ожидания.
- Условие «подписка действует» определено в одном месте (константа `activeSubscription`), и тест проверяет, что список и точечная проверка доступа не расходятся.

**SQL.** Пользовательские значения передаются в запросы только параметрами (`?`). Конкатенацией склеивается лишь неизменная константа с условием подписки, поэтому SQL-инъекция невозможна.

**Ошибки.** Подробности (текст ошибки БД и т. п.) пишутся только в лог, клиенту отдаётся общее сообщение. В логи не попадают пароли и заголовок `Authorization`.

**Таймауты сервера** (`ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`) заданы явно, чтобы медленные клиенты не держали соединения бесконечно.

**Корректная остановка.** По SIGINT/SIGTERM сервер перестаёт принимать новые запросы, ждёт завершения текущих (до 10 секунд) и затем закрывает БД. В Docker сервис запущен как PID 1 в exec-форме, поэтому `docker stop` доставляет сигнал напрямую.

**Тесты** проверяют поведение на настоящей SQLite, а не на моках: так проверяется и SQL. Тесты уровня `store` проверяют правила доступа (истечение, ручное выключение, граница срока), тесты уровня `api` проверяют коды ответов и формат JSON.

**Известные ограничения.**
- Basic Auth без TLS передаёт пароль открытым текстом: в проде сервис должен стоять за прокси с HTTPS.
- Ответ `405 Method Not Allowed` формируется стандартным `ServeMux` и приходит текстом, а не в формате JSON.
- Один экземпляр сервиса и SQLite-файл: для нескольких экземпляров нужна общая БД (например, PostgreSQL).
- Каждый запрос проверяет пароль через bcrypt и ходит в БД: под высокой нагрузкой это станет узким местом (см. «Что бы я улучшил»).

## Что бы я улучшил

- Кэш результатов аутентификации и списка каналов с защитой от лавины одинаковых запросов.
- Админ-API или панель для управления пользователями, каналами и подписками.
- JSON-формат для 405 и для паники в хэндлерах (recover middleware).
- Лог каждого запроса (метод, путь, статус, время) с идентификатором запроса.
- Ограничение частоты попыток входа по логину и IP.
- Версионируемые миграции схемы вместо `CREATE TABLE IF NOT EXISTS`.
- PostgreSQL и TLS для работы в нескольких экземплярах.
